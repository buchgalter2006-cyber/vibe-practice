# PLAN_F5.md — фаза 5 «Сервис»: загрузка ведомости и роли доступа

> План написан 23.09.2026 (сессия-планирование), реализуется в отдельной сессии. Источник правды для исполнителя.
> Рабочая база: каркас Ф3 (`app/`), источники Ф4 (`app/services/`, `stub/`). Вид интерфейса — из `mockup/`, менять минимально (только новые блоки на «Настройках» и страница логина в том же стиле).

## 1. Что делаем

Два среза в одной фазе:

1. **Загрузка Excel-ведомости через интерфейс** (drag-and-drop на вкладке «Настройки») вместо пути в `.env` + журнал импортов.
2. **Авторизация с ролями** — три уровня доступа: `admin` / `editor` / `view`.

**НЕ делаем:** деплой (Ф6), агентов (Ф7), смену стека, редактирование существующих вкладок дашборда.

## 2. Срез 1 — загрузка ведомости

### API

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/upload/fact_marketing` | multipart-файл (.xlsx): валидация → атомарная замена `data/fact_marketing.xlsx` → запись в `import_log` |
| GET | `/api/imports` | последние 20 записей `import_log` (новые сверху) |

Валидация загруженного файла (порядок важен, каждая ошибка — понятный текст):
1. Расширение `.xlsx` (иначе 400 «нужен .xlsx»).
2. `load_workbook` из потока (`openpyxl.load_workbook(BytesIO)`) — битый файл → 400.
3. Лист «Факт маркетинга» (или активный), шапка в строке 2, месяцы совпадают с датасетом.
4. Каналы совпадают с планом (тот же набор, без дублей).
5. Значения — числа ≥ 0.
6. **Контрольная сверка**: агрегат по месяцам из файла сравнить с текущим `data/fact_marketing.xlsx`-фактом — если расхождение > 50%, ответить 400 с текстом «похоже, не та ведомость» (защита от загрузки не того файла; порог в константу).

Успех: сохранить файл через временный файл + `os.replace` (атомарно), в `import_log` строку `source='excel_file', rows_imported=N, status='ok', message='<имя файла>'`. Ошибка валидации: `status='error', message=<причина>`, файл не заменять, HTTP 400 с текстом.

Кэш источника Excel — по mtime, после замены файла подхватится сам; дополнительно сбросить кэш `_xlsx_cache` активного источника, если он реализует метод `reload()` (добавить его).

### Интерфейс (вкладка «Настройки»)

- Блок «Загрузка ведомости факта»: зона drag-and-drop + клик (input file, accept=.xlsx), статус-строка результата (зелёная/красная).
- Таблица «Журнал импортов» (GET /api/imports): время, источник, строк, статус, сообщение.
- После успешной загрузки — автообновление вкладки «Маркетинг» при следующем переключении (данные тянутся с API при показе).

## 3. Срез 2 — авторизация с ролями

### Модель

- Таблица `users`: `username PK, password_hash, role, created_at`. Пароли — `werkzeug.security.generate_password_hash` (pbkdf2).
- Роли и права:
  - `view` — только GET `/api/meta|overview|marketing|sales|metrics` и страницы дашборда;
  - `editor` — всё из view + загрузка ведомости + чтение/сохранение настроек и нормативов (GET/PUT `/api/settings`) + `/api/imports`;
  - `admin` — всё из editor + управление пользователями.
- `GET /api/whoami` → `{user, role}` или `{user: null}`.

### Сессии

- Flask `session` (cookie), `SESSION_SECRET` из `.env` (сгенерировать и добавить в `.env` и `.env.example`; в git не попадает).
- Страница `/login` — в стиле приложения (тот же CSS): карточка по центру, логин/пароль, ошибка инлайн. После логина — редирект на `/#overview`.
- `/logout` (POST) — очистка сессии.

### Пользователи

- При первом старте, если `users` пуста: создать `admin` с паролем из `.env` `ADMIN_PASSWORD` (добавить в `.env`: `ADMIN_PASSWORD=admin-start-2026`), роль admin. В README и `.env.example` зафиксировать, что пароль меняется через управление пользователями.
- API управления пользователями (только admin):
  - `GET /api/users` — список (без хэшей);
  - `POST /api/users` — создать `{username, password, role}` (валидация: длина пароля ≥ 8, роль из трёх);
  - `POST /api/users/<username>/password` — сменить пароль (себе — любой ролью, другим — только admin);
  - `DELETE /api/users/<username>` — нельзя удалить себя и последнего admin.

### Проверка доступа (декоратор)

- `require_role("editor")` и т.п.: не залогинен → 401 `{"error": "требуется вход"}`; роль ниже → 403 `{"error": "недостаточно прав (нужно: editor)"}`.
- На `/api/upload/*`, `/api/imports`, PUT `/api/settings` — `editor`; на `/api/users*` — `admin`; остальные GET — публично (в этом проекте данные синтетические).

### Интерфейс

- В сайдбаре внизу — блок пользователя: «Вы вошли как <имя> (<роль>)» + кнопка «Выйти»; для `view` пункт «Настройки» скрыт.
- Страница логина показывается приложением при 401 от API (redirect на /login).
- На «Настройках» — секция «Пользователи» (только для admin): список, создание, смена пароля.
- Загрузка ведомости и сохранение настроек скрываются для `view` (проверка и на клиенте по `/api/whoami`, и на сервере — обязательно).

## 4. Критерии приёмки

- [ ] Загрузка валидной ведомости: файл заменён, `/api/marketing` отдаёт новые цифры, запись в `/api/imports` со статусом ok
- [ ] Загрузка не-того файла (например, план вместо факта или изменённые каналы) → 400 с понятным текстом, файл НЕ заменён, в журнале error
- [ ] Загрузка .pdf/.docx → 400 «нужен .xlsx»
- [ ] Без логина: `/api/upload/*` → 401, PUT `/api/settings` → 401, дашборды открываются
- [ ] Логин admin → всё доступно; логин view → Настройки скрыты, PUT/upload → 403
- [ ] `/api/users`: создание editor, смена пароля, нельзя удалить последнего admin (400)
- [ ] Пароли не хранятся открыто; `/api/users` не отдаёт хэши; секреты в логи не пишутся
- [ ] `data/app.db` и `.env` в `.gitignore` (проверить)
- [ ] Скриншоты: страница логина, «Настройки» с зоной загрузки и журналом, дашборд после загрузки
